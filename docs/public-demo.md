# Public view-only demo

`canonry demo` serves the real Canonry dashboard with fictional sample data and no sign-in. It creates a fresh in-memory SQLite database on every start. It does not read an existing Canonry database or configuration, accept credentials, or run providers, telemetry, scheduled jobs, OAuth callbacks, MCP, or the Aero agent. The Aero bar shows a scripted preview on the sample data instead: its four starters (Status, What changed, Biggest gaps, Top insights) replay turns written at startup from the seeded records, with no model calls.

```sh
canonry demo
canonry demo --host 127.0.0.1 --port 4188 --format json
```

The default address is `http://127.0.0.1:4188`. Use a dedicated process and reverse proxy to publish that listener over HTTPS. `--host`, `--port`, and `--trust-proxy` are explicit; the normal `CANONRY_HOST`, `CANONRY_PORT`, and configuration-directory environment settings do not select the demo's listener or data. Stop with SIGINT or SIGTERM. The foreground server command has no MCP counterpart because starting a public listener is a host operation, as with `canonry serve`.

## Rate limit and reverse proxies

The rate limit is the demo's abuse control, and it counts per client IP address: 600 requests a minute for each visitor. Every API request counts, including HEAD requests, refused changes, and requests for unknown or malformed paths. Built browser assets, the icons, and the dashboard page itself do not.

The demo takes the visitor address from `X-Forwarded-For` only when the connection comes from a trusted proxy. By default it trusts `127.0.0.1` and `::1`, which is a reverse proxy on the same machine. For a proxy on another address, name it with `--trust-proxy`, once for each address or CIDR range. The values replace the default, and every proxy hop between the visitor and the demo must be listed. A value, or set of values, that covers every IPv4 address or every IPv6 address is refused in any spelling, such as `0.0.0.0/0`, `::/0`, or the IPv4-mapped `::ffff:0:0/96`, because it would let any visitor choose the address they are counted under.

```sh
canonry demo --host 10.0.0.20 --trust-proxy 10.0.0.5 --trust-proxy 10.0.1.0/24
```

The limit is only per visitor when the real visitor address reaches the reverse proxy, and the reverse proxy must pass it on in `X-Forwarded-For`. If a TCP or TLS passthrough (such as an SNI router or layer 4 load balancer) sits in front of the reverse proxy without PROXY protocol, the reverse proxy sees the passthrough's address on every connection. Every visitor then shares one budget, so one busy visitor can lock everyone out for the rest of the minute. Terminate TLS at the first hop, or enable PROXY protocol between the passthrough and the reverse proxy.

The examples include a standard service business and a custom portfolio containing 12 properties across three markets under one domain. Visitors can browse stored AI answers and citations, compare providers, inspect property and query assignments, explore search and indexing evidence, page health, traffic, local presence, conversion configuration, research, backlinks, and reports. All example business domains use `.example`. The standard business has six weekly sweeps across three answer engines over eight non-brand and two branded queries. One engine climbs, one holds steady before a dip and a recovery, and one swings from week to week. Mentions and citations are planned separately, so some answers name the business without citing its site and others cite a page without naming it. Its health history and insights come from the production analysis of those stored answers. The standard business Site Health map contains 205 pages on summit-roofing.example: services and sub-services, 24 invented service towns with town-by-service pages, completed projects, guides, financing, reviews, careers, and the quote flow. It shows faults a small business site tends to carry: moved URLs that older pages still link to, broken links, noindex quote and confirmation steps, paginated guide archives whose canonical points at the guide index, thin pages, and pages found only through the sitemap. The portfolio Site Health map contains 604 pages: destination hubs and guides, plus 48 pages for each property, covering rooms, dining, amenities, experiences, offers, meetings, and practical information, with examples of broken links, redirects, PDFs, and intentionally hidden pages. Both maps come from one shared crawl seeder that stores menu and footer links, page audits on the factors a real audit reports, and the same crawl vocabulary a real scan writes. Page lists and scorecards derive from the same crawl evidence. A bounded offline worker computes the layout using the production graph engine at startup; no website is crawled. The persistent demo notice distinguishes this sample from customer results. Runtime conversion verification remains unverified; stored configuration cannot prove that a browser event fired.

Only explicitly allowed GET and HEAD routes are exposed. Every other HTTP method is refused before handlers execute. SQLite is switched to query-only mode after seeding. The server supplies the dashboard with a fixed synthetic read-only principal; bearer tokens and cookies do not grant additional permissions. Provider-backed GET routes and administrative/settings reads are refused as well. The scripted Aero preview is one stored read, `GET /api/v1/projects/:name/agent/preview`; the live agent routes for prompts, transcripts, providers, and conversations stay closed. Bing performance and coverage use stored sample rows because the ordinary routes would contact Bing or persist a derived snapshot. Static files are confined to bundled browser assets and three named public icons.

Data is dated relative to process startup. Restart the dedicated demo process regularly to keep recent-date filters populated; restarting creates only synthetic data and performs no external queries. There is no customer data to back up. Do not point a normal `serve` instance at customer data and remove its authentication to recreate this behavior.

For local development, run `pnpm build:web` first, then `node --import tsx packages/canonry/src/cli.ts demo`. For a complete distributable, use `pnpm build`. The demo browser assets are the same build used by the normal server.
