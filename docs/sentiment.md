# Experimental sentiment

Sentiment classifies stored English answers for a specific frozen subject. Branded and non-brand queries have separate scores and denominators. It is disabled by default at both install and project levels. It does not change citation or mention measurements, pool branded with non-brand queries, or run a new answer-engine sweep. Independent held-out human evaluation has not been completed; these results remain experimental.

## Enablement and authority

The private install `config.yaml` accepts:

```yaml
sentiment:
  enabled: true
  model: jev-1.13.0
  maxConcurrency: 2
  maxRequestsPerMinute: 60
  maxInputTokensPerMinute: 100000
  maxAttempts: 3
```

Supply `TYPESAFE_API_KEY` in the server environment, or `sentiment.apiKey` in private install configuration. Never put it in a project export, source repository, command argument, or browser configuration. `CANONRY_SENTIMENT_ENABLED` can explicitly override install enablement; `TYPESAFE_MODEL` must remain `jev-1.13.0`. The worker rereads configuration before each dispatch. Routine configuration saves, such as a Google token refresh or a provider settings change, keep the `sentiment` block exactly as it is on disk, so they never undo a live disable, removal or key rotation. Disabling prevents subsequent requests and cancels pending selections; re-enabling does not resume canceled work. A missing, unreadable or invalid `config.yaml` (for example a misspelled key or an out-of-range limit) also stops requests and reports `invalid-config`, but it holds pending work instead of canceling it; fixing the file resumes that work, including completions from the gap. A missing key or unsupported model holds the same way. Only an explicit `enabled: false` cancels.

An install administrator must also configure the project:

```bash
canonry sentiment settings example --format json
canonry sentiment configure example --enabled true --format json
```

Enabling automatically admits eligible completions after the enablement boundary. Old answers require an explicit preview and backfill. Only enabling depends on the install: an install administrator can switch a project off at any time, including while the install switch is off, so re-enabling the install never resumes a project that was withdrawn. Named viewers, read-only keys, project-scoped keys, and narrow write keys cannot configure or admit work. Delegated requests retain their underlying user's role. The read surfaces obey the existing project boundary.

Enabling and backfill send each selected answer's stored text to TypeSafe with the frozen subject identity (name, aliases, qualified aliases and URLs), the tracked query text and query class, the answer engine with its requested and served models, the location, and internal query, subject, Property, group and market identifiers, and may incur usage. A preview selects exactly one query class: the CLI requires `--query-class branded|non-brand` and the MCP preview tool requires `queryClass`, so backfilling both populations of a history takes one preview and one submission per class. Inspect the preview, including its echoed `selection` and every `skipped` reason, before submitting its token with a stable idempotency key:

```bash
canonry sentiment backfill example --preview --run-id saved-run --query-class non-brand --format json
canonry sentiment backfill example --preview-token TOKEN --idempotency-key operator-action-1 --format json
canonry sentiment jobs example --format json
canonry sentiment example --run-id saved-run --query-class non-brand --format json
canonry sentiment evidence example --run-id saved-run --query-class non-brand --query-id saved-query --format json
```

A preview reports every answer it leaves out in `skipped`, by run and reason: probe, failed and incomplete sweeps, sources saved without frozen provenance (`legacy-missing-provenance`), Advanced sweeps saved before the answer language was recorded (`legacy-missing-language`, never assumed from today's project language), and the other query class's answers (`excluded-branded` or `excluded-non-brand`). A preview with nothing eligible returns no token. A never-configured project is estimated against the evaluator that enabling would create. A date range that matched no runs keeps its bounds.

Identical authorized retries return the same job receipt, including after preview expiry or disablement. A changed payload with the same key conflicts. Explicit new backfill can renew an exhausted or canceled attempt budget while retaining lifetime attempt history.

## Measurement and provenance

Favorable rate is favorable divided by favorable + mixed + unfavorable. Mixed receives no favorable credit. Zero judged answers produce unavailable rates, not zero percent. Counts explicitly partition judged, excluded, pending, failed, canceled, and unadmitted assessments. A 95% Wilson interval describes the judged proportion; it does not include classifier error or correlation among repeated answers.

The initial feature measures overall stance only; there are no theme presets or custom theme settings. The evaluator asks five questions about identity, judgment, stance, conclusion evidence, and a complaint quotation. Evidence consists only of original sentence spans. A period after a common abbreviation (Dr., St., e.g., U.S.) or a single-token list marker (1., iv.) does not end a span, so a quotation is never a bare fragment. Invalid conclusion evidence abstains. Request size is estimated as UTF-8 bytes / 2.5 plus 1024 tokens. A request above 64,000 estimated tokens, state plus its longest question above 32,000, or an answer with more than 254 sentences is recorded as `input-too-large` and never truncated; a provider context rejection is a permanent failure. Complaint quotations are separate from the overall conclusion.

A known intended subject absent from the answer yields `subject-not-mentioned`, outside the judged denominator. Non-brand answers with no shared-matcher hit for any frozen alias, qualified alias, or URL hostname abstain locally without a provider request. A Simple subject's aliases are the same effective brand names the mention metric uses, display name included, so an answer that names the brand only by its display name is sent, not recorded as absent. That list keeps one spelling per brand key, so of "Acme NYC" and "AcmeNYC" the evaluator sees only one. A Simple subject's qualified aliases are the operator-chosen subset of project aliases frozen at dispatch, sent with their exact spellings; they change what the evaluator is told, not which answers are sent: the local non-brand check already matches every alias. Missing frozen identity is separately inapplicable. Mention detection does not assign stance: a matching but ambiguous name still requires identity resolution.

Simple assessments use frozen run-sidecar identity and query class. Advanced assessments use the frozen plan revision, execution node, Target/Property, query assignment, location, and exact group/market usage edges. One shared answer can yield opposite verdicts for two subjects. Overlapping markets count an answer-subject assessment once. Deleting a tracked query or editing current project identity does not rewrite the saved evidence.

Qualified aliases are set with `canonry project update <name> --add-qualified-alias <alias>` (and `--remove-qualified-alias`), `qualifiedAliases` on the project API, or `spec.qualifiedAliases` in `canonry apply`. Each entry must already be a project alias; any spelling of the display name (same brand key), a brand key shorter than four characters, and a competitor's name are refused. A later change that disqualifies a stored entry without sending the list drops it: removing the alias, renaming the display name to a spelling of it, or adding a competitor with its brand key through the API, discovery, or `canonry apply`. Setting them applies to later runs only: history is not rescored. Each run's sidecar is immutable, so a backfill of an earlier run uses that run's frozen list, and answers it already classified count as `alreadyClassified` and are not sent again.

Complete initial sweeps (sync or batch dispatch) and completed fills publish durable completion receipts, including superseded fills. Each receipt commits with the status write that completes the run, so a completed run records exactly one. Incomplete, probe, failed, and legacy sources without required provenance cannot silently supply the headline. Unsupported language, absent text, ambiguous identity/judgment, factual answers, and oversized input have explicit outcomes. Full input is not silently truncated.

## Reads, retries, and comparison

HTTP exposes nine capabilities under `/api/v1/projects/:name/sentiment`: settings GET/PUT, summary GET, evidence GET, compare GET, backfill-preview GET, backfills POST, jobs GET, and job detail GET. The generated SDK, CLI, and monitoring MCP toolkit expose the same capabilities. Dashboard selectors retain the same frozen scope. `queryId` is a selection identity on summary, evidence, comparison, and preview, and so is `executionNodeKey` (`--execution-node-key`), the exact Advanced execution node of that query. Summary responses include server-computed per-query scores with frozen source membership. Query rows are sorted by query text and paged: `queryLimit` rows (default 25, at most 500; `--query-limit`), with `queryPage.nextCursor` passed back as `queryCursor` (`--query-cursor`). Advanced rows are per execution node and carry `executionNodeKey`. Per-engine `assessments` and per-location scores are opt-in with `include=assessments,locations` (`--include`), and come by default when `queryId` names one query. Breakdowns cover engine, Property and market; query rows are not repeated there. The jobs list returns the newest 100 job summaries with outcome counts and an `attemptCount`; the job detail pages its attempt receipts, newest first (`attemptLimit` default 50, `nextAttemptCursor`, `--attempt-limit` and `--attempt-cursor`). The default read class remains branded for compatibility; select `queryClass` explicitly for non-brand. New completed runs admit both classes separately. Summary and evidence can select an exact saved run group using `runIds` (repeated HTTP query keys), mutually exclusive with `runId`; the CLI spelling is repeated `--run-ids <id>`, and MCP takes an array. Evidence cursors include this group identity. Included `assessments` carry the exact source snapshot, engine/model, frozen subject, state and outcome; original answers and quotes remain in the evidence endpoint. Its optional `assessmentId` selector (`--assessment-id` in the CLI) reads one assessment within the existing project, source, evaluator and scope boundaries, and participates in cursor identity. Reads and previews never invoke Jev.

The CLI and the MCP adapter read every sentiment response with tolerant readers (`packages/contracts/src/sentiment-read.ts`): a field added by a newer server is dropped, a new state or outcome reads through as a string, and a count keyed by a new outcome is kept. A globally installed CLI or MCP adapter therefore keeps reading an engine that updated on its own. The server's own DTOs stay strict.

Project overview reads of a project whose sentiment is off (the default) answer from its settings alone, and a configured overview selects each run once per class. Leases and shared SQLite reservations bound requests across projects. A rate limit (429) or a refused credential (401/403) pauses dispatch for the whole install, and the refused assessment is requeued outside its retry budget. After a rate limit the pause lasts 30 to 60 seconds, doubles with each further one up to 15 to 30 minutes, and a longer `Retry-After` wins. A refused credential pauses until the configured key changes, testing the provider with one request an hour. When a pause ends, one request tests the provider before normal concurrency resumes. Settings report a credential pause as `provider-authorization` (not ready, so no backfill is admitted) and a rate-limit pause as `provider-rate-limit` with the time dispatch resumes. Automatic work is claimed ahead of backfills, and claims rotate across projects, so one project's long backfill never holds another's new sweep. Each completion receipt is reconciled once. Every started remote attempt has a durable receipt. Reported usage enters the existing `typesafe`/`sentiment` ledger; interrupted or uncertain billing remains unknown. Recovery can create another billable attempt and does not imply exactly-once remote billing. The lifetime attempt history is retained independently of a newly authorized retry budget.

Comparisons return both period summaries with every matched query row in compact form; per-engine and location detail stays on the paged summary read. They match frozen units and refuse a directional claim across incompatible evaluator, subject, source-model, execution-context, query-class, or population boundaries. Every change to a project's qualified aliases (first set, edit, or clear) starts a new subject boundary at the first run captured afterward: a pooled read across it is unavailable with `subject-identity-changed`, and a comparison across it refuses with `source-scope-changed`. Read windows that start at the most recent change. A local abstention that never reached TypeSafe (for example an absent non-brand subject) has no classifier model and never counts as a classifier change; only two different models that did answer refuse with `classifier-model-changed`. Evidence cursors bind the entire selection and resolved evaluator. New answer text under unchanged measurement/evaluator identity remains comparable.

## Dashboard placement

When project sentiment is configured and has judged assessments, portfolio project rows show one Sentiment percentage: the favorable share across branded and non-brand queries. The server computes this score from distinct answer-subject assessments, rather than averaging the two class rates; the tooltip names the combined scope and its denominator. A measured 0% remains visible; unavailable overall scores have no metric or reserved column. Embeds hide the portfolio figure, as they hide sentiment on the project page. Overview scores use the same latest completed location-run group as visibility and expose its `runIds`. The API, `canonry overview --format json`, and `canonry_project_overview` return the additive `sentiment.overall` headline with `queryClass: all`, alongside the unchanged `branded` and `nonBrand` headlines. Human CLI output prints the server's overall score, judged denominator, and provisional state. Older responses without `overall` remain readable and do not trigger a client-side calculation.

Simple Query evidence and Advanced Property/query views keep separate class headlines, branded first, each with its rating count and per-query Favorable values. Closed Details sections hold coverage, nonjudged outcomes and confidence ranges; empty classes show a short state without zero-count rows. Data-processing disclosure appears in Enable/Manage sentiment. Every percentage, intervals included, uses the shared percent format (one decimal; 199 of 200 reads `99.5%`, never `100%`). Selecting a value opens the source evidence. Advanced scope retains the exact Property, market, run, and revision. A Simple project page resets any Property, group or market scope carried in from an Advanced URL to the whole project. The combined portfolio sentiment score does not change class-specific sentiment reads, comparisons, or competitive visibility metrics.

Expanded Simple query rows show each engine answer’s stored verdict. The Answer engine selector scopes the displayed answers, saved run membership, class headlines, query scores and evidence together. An empty engine/location intersection stays unavailable. Advanced engine rows use exact source snapshot IDs and label each measured subject separately when Properties share an answer. Selecting an engine verdict opens that exact assessment’s quotations; unclassified, factual and absent-subject states never imply an unfavorable judgment.

Jev is the common evaluator; the engine and model shown with each verdict identify the original answer source. Existing summary reads supply all engine labels, without a separate request for every row.

Manage sentiment opens the enablement and backfill controls from the existing view. There is no additional sentiment tab. A dashboard backfill covers the whole chosen sweep for the chosen query class: every engine, model, location, query and Property. The engine, model, location, Property, group, market and revision filters on screen apply only when the administrator checks "Limit to the current view". The preview shows the selection the server actually covered and lists what it skipped and why, including when nothing is eligible.

Disabled projects hide these scores. While the project or the install is off, API, CLI and MCP reads keep operational states (pending, running, waiting to retry, failed, canceled) but withhold every verdict, quotation and outcome count: evidence pages return no items and job counts keep only the operational states. Zero judged answers show Unavailable, and so does a view with no saved source evidence. The dashboard re-reads the two class summaries every 5 seconds only while assessments are pending, running or waiting to retry, or while a job the administrator can see is active. Failed and canceled assessments are terminal, so a partial result alone does not keep it polling; returning to the page re-reads both summaries. The server owns all percentages, counts, location slices, and source deduplication.

## Historical evaluator compatibility

The stance-only evaluator has schema version 2 and a new immutable definition ID. Stored version 1 results remain readable through a projection that omits retired theme fields without changing their stored JSON, schema version, or evaluator identity. Existing version 1 queued work cannot dispatch under version 2 semantics; new work requires explicit admission under the current definition. The same holds for a version 2 definition frozen under an earlier request template (for example `qualified-subject-v2` identity or `sentence-spans-v1` segmentation): its results stay readable, settings report `unsupported-evaluator-definition`, and nothing new is admitted or sent under it. Configuring sentiment again creates the current definition, starts a new enablement epoch and cancels work still queued under the old one. Comparisons across definitions refuse a directional claim.

## Validation and release gates

See [sentiment smoke validation](sentiment-validation.md) for reproducible built-package tests and the recorded synthetic live smoke. Aero routing and downstream reports remain follow-on work. Branded and non-brand accuracy require separate held-out evaluations; neither has passed that gate. Production rollout and claims of measured classifier quality require the independent evaluation rubric in `evals/sentiment/`; synthetic smoke is not that evaluation.
