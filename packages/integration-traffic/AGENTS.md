# integration-traffic

## Purpose

Provider-neutral traffic classifier and rollup. Takes `NormalizedTrafficRequest` events (from any traffic adapter — Cloud Run today, WordPress/Cloudflare/Vercel later) and produces hourly crawler / AI-referral buckets plus a debugging probe report. Lives between the raw adapters and the future DB persistence layer.

## Key Files

| File | Role |
|------|------|
| `src/rules.ts` | Bundled AI crawler UA patterns and known AI-referrer host rules |
| `src/classifier.ts` | `classifyCrawler` / `classifyAiUserFetch` / `classifyAiReferral` — three disjoint matchers. `classifyCrawler` matches UA rules with `purpose !== 'user-agent'` (GPTBot, OAI-SearchBot, …). `classifyAiUserFetch` matches UA rules with `purpose === 'user-agent'` (ChatGPT-User, Perplexity-User) so per-user fetches stay separate from bulk crawl. `classifyAiReferral` matches referer host or `utm_source` against known AI domains **and** stamps a paid/organic `trafficClass` via `classifyAiReferralTrafficClassFromEvent`, which reads `utm_medium`/`utm_campaign`/`utm_content`/`utm_term` off both the request and referer query strings through the shared `classifyAiReferralTrafficClass` (contracts). The class is orthogonal to `evidenceType` (which only identifies the engine): the referer host says WHO sent the click, the UTM tags say whether it was PAID. `organic` means "no paid evidence", never "confirmed unpaid" — an untagged ad click is indistinguishable. There is no server-side equivalent of GA4's `channelGroup`, so the UTM tokens are the only discriminator. Crawler/user-fetch matchers return `claimed_unverified` until IP verification promotes to `verified`. |
| `src/ip-range-manifest.ts` | Strict, full-string IPv4/IPv6/CIDR parsing, pure publisher-manifest validation, and canonical prefix-content hashing. The refresh script and runtime verifier share this fail-closed boundary. |
| `src/ip-verify.ts` | Maps classifier rules to vendored publisher manifests and returns the verification decision with exact manifest provenance. |
| `src/rollup.ts` | `buildTrafficProbeReport` — aggregates classified events into hourly buckets + top-N summaries. Verified crawler/user-fetch bucket identity includes the publisher manifest id, and each bucket carries that manifest provenance. AI-referral buckets carry `paidHits` / `organicHits` alongside `hits` (`paidHits + organicHits === hits`); a session is paid when ANY hit in its window is paid (the ad UTMs ride the landing request; the follow-up sub-resources carry none, so a later tag-less hit must not downgrade it). AI-referral sessions count arrivals, by the journeys' rule (`findAiReferralFollowOns`): a request whose referer is outside the site is an arrival; one with a same-site referer (`isStepReferer`) that still carries the engine's utm is a later page, asset or API call of a visitor already on the site, a follow-on of any arrival of that visitor from the same engine within `AI_REFERRAL_LOOKBACK_MS` (the 30-day journey lookback) and the arrival itself only without one: it stands in for a landing the logs never saw (the cached-site case). A landing from outside is not counted again when a stored stand-in falls within `AI_REFERRAL_SAME_VISIT_MS` after it (its own later request reached ingest first). A Location redirect is a hop, never the arrival. Follow-ons stay in `aiReferralHits` but never open a session. Callers pass `aiReferralFollowOnEventIds` planned with stored arrivals (`api-routes/src/ai-referral-arrivals.ts`); without it, follow-ons are found within the batch. |
| `src/journey.ts` | AI visitor journeys, pure core. `extractJourneyRequests` keeps a batch's browser requests (no crawlers, AI user fetches, self traffic, non-browser clients, static assets, HEAD/OPTIONS), normalizes times to UTC ISO, cuts queries to `utm_*` and keeps click ids by presence only. `maskJourneyPath` masks secret-like path segments. `sessionizeJourneyRequests` groups one visitor's requests into 30-minute visits (`placeRequest` applies the in-order rules, so a late request joins or heads the right visit, and a late outside arrival inside a stored visit records `splitFrom` so the caller moves that visit's later requests) and keeps requests within 30 days after an AI touch plus the rest of a kept visit, capped per visitor per UTC day. AI touches are never capped and are marked on each event write, so the lookback can be rebuilt exactly. A same-site, sign-in, payment or booking-engine referer is a step (`isStepReferer`, shared with the AI-referral rollup; `STEP_REFERER_HOSTS`: transaction-only hosts, never listing marketplaces); an AI engine seen only on a same-site utm counts as a touch only without an AI touch in the lookback; a background data call (API or JSON) never opens or heads a visit and is never an AI touch, because it carries its page's referer and utm tags (only the page is the arrival); at the same instant a page sorts before its calls. An arrival seen only on calls (its page never logged) is lost. Bump `JOURNEY_RULES_VERSION` when a change would alter stored journeys. A late request does not merge two stored visits, and push requests dropped before the AI landing arrives are not recovered. Keying and storage live in `api-routes/src/journeys.ts`. |
| `src/types.ts` | Bucket shapes (`CrawlerEventHourlyBucket`, `AiReferralEventHourlyBucket`), classifier output types, probe report shape |
| `src/agent-trust.ts` | `assessAgentTrust`, `isScannerPath`, `withScannerBurst` and `AGENT_TRUST_RULES_VERSION`; see "Agent trust" below. |
| `src/browser-agents.ts` | `browserAgentRequestKind`: what a hosted browser agent's request was (a page load, an action such as a form post or checkout, or a resource its page fetched or sent by itself; the kinds are contracts' `BrowserAgentRequestKinds`, re-exported here). `countsAsAiUserFetchHit` and `keepsBrowserAgentJourneyRequest` apply it to counts and journeys; also `BROWSER_AGENT_REQUEST_RULES_VERSION`, `BROWSER_AGENT_BOT_IDS` and `isBrowserAgentId`. See "Browser agents" below. |
| `src/scanner-bursts.ts` | `findScannerBursts`: unverified agent requests from a client (one IP) that asked for a scanner path within `SCANNER_BURST_WINDOW_MS` (10 minutes). Callers pass stored windows (`known`) so bursts split across batches read the same; `findScannerBurstsInBatch` is the default within one batch. |
| `src/agent-journeys.ts` | `extractAgentJourneyRequests`: user-triggered AI fetches only, excluding likely fakes, preserving document/API requests, failed requests and HEAD. Static assets and self-traffic are excluded. A browser agent keeps its page loads, its actions and any request that failed (see "Browser agents"). Queries/fragments are dropped and paths use `maskJourneyPath`; raw IP/UA remain transient inputs for keyed correlation, never stored event fields. |
| `src/index.ts` | Re-exports public API |

## Patterns

- **Pure functions, no I/O.** Adapters fetch and normalize; this package only classifies and rolls up. Unit-testable end-to-end with fixture events.
- **Three evidence channels.** Bulk crawl via UA where `purpose !== 'user-agent'` (`crawler_events_hourly`); per-user AI fetches via UA where `purpose === 'user-agent'` (`ai_user_fetch_events_hourly`); human AI referrals via referer/UTM (`ai_referral_events_hourly`). Never collapse them — each answers a different question: "is AI training on me?" vs. "is AI reading me for a user right now?" vs. "are users clicking through from AI?"
- **Verification status tiers.** A UA-only match stays `claimed_unverified`; it is promoted to `verified` only when the source IP falls in the operator's published range (see `ip-verify.ts`). `verifyIpForRuleDecision` also returns the exact vendored manifest consulted; its id combines source, publisher version, and a canonical SHA-256 prefix-content digest so stale publisher versions cannot merge different snapshots. Classifier results and hourly buckets preserve it as `verificationManifest`, including rejected decisions, so historical rollups remain attributable when publishers change their ranges. User-fetch agents are a caveat: an on-device fetch egresses from the user's own IP, so a genuine user fetch can stay `claimed_unverified` permanently. The `unknown_ai_like` bucket is reserved for behavioral heuristics.
- **Agent trust (user-triggered agents).** `agent-trust.ts` gives every `classifyAiUserFetch` result a `trust` level and `trustReasons`. An IP in the published list is `verified` and wins over every other signal. Otherwise any of these makes it `likely_fake`: a scanner path (`isScannerPath`: hidden files and folders except `.well-known` and Netlify's served routes, `.env` files, directory traversal, `/proc/self`, mounted cluster secrets, framework debug consoles, `wp-login.php`, `xmlrpc.php`, `phpmyadmin`, and, at the site root or in a config or key folder only, credential, key and server-settings files such as `service-account.json`, `config/production.json` or `id_rsa`; a browser agent's app files are spared, see "Browser agents"), or a user agent that differs from the rule's `documentedUserAgents` (set only when the operator labels the string as its FULL user agent, currently OpenAI ChatGPT-User and MistralAI-User). An IP missing from the published list is never a fake signal on its own: Anthropic publishes a rotating snapshot of single addresses (a refresh dropped 22 of 26), and every vendored list lags real egress; such a request is `unknown`. An unchecked request (no IP or no list) with the documented user agent is `likely_real`; the rest is `unknown`. `assessAgentTrust` judges each request alone. The one cross-request signal is the scanner burst: an unverified agent request from a client (one IP) that asked for a scanner path within 10 minutes is `likely_fake` with `scanner-burst` (`findScannerBursts`, applied with `withScannerBurst`). Ingest keeps each client's latest probe window (`agent_scanner_clients`, a keyed hash of the IP) so a one-event push or a batch boundary reads like one batch; the only gap is a request stored in an earlier batch before its client's first probe. Verified requests are never marked or used as probes. Rollups, samples and agent journey capture all read `classifyAiUserFetch` with the same burst marks, so likely fakes go only to `aiUserFetchLikelyFakeHourly` (keyed by first reason) and never to AI user fetch buckets or journey events. Bump `AGENT_TRUST_RULES_VERSION` when the rules change, so stored traffic is checked again. Test fixtures must use the operators' real user-agent strings; a shortened `ChatGPT-User/1.0` is now an unusual format.
- **Browser agents (`AiCrawlerRule.browser`: Google-Agent, Claude-Agent).** A hosted browser acting for a person loads a page the way a person's browser does: one page load brings its scripts, styles, images, framework data, prefetches of the links in view and analytics beacons, about twenty requests where a link fetcher (Claude-User) makes one. Decided 2026-11-11 (follow-up to Canonry/canonry#1517), with the owner choosing the trust and history options below:
  - **Counting.** `browserAgentRequestKind` reads the method first, then the query, then the path; the lists it applies, and why each entry is there, are the constants in `browser-agents.ts`. HEAD and OPTIONS are resources. Any other method but GET is an action wherever it goes, unless it is a page's background write (Vercel analytics beacons, anything sent to `/cdn-cgi/`, WooCommerce and Heartbeat AJAX). A GET is a resource when its query marks a page's own fetch, a page when it opens a document or a download wherever it is kept, a resource when its path is one a page fetches by itself (static files, framework, platform and CMS folders at any depth, `/api/` and `/graphql` as the first segment only), and otherwise a page. Only page loads count as AI user fetch hits and hourly buckets (`countsAsAiUserFetchHit`, after likely fakes are routed to their own counts). Resources and actions go to `totals.aiUserFetchBrowserNonPageHits` and to no bucket; api-routes reports that count on every write path (its "Traffic ingestion"). Each browser-agent sample records its `requestKind`. Link fetchers still count every request.
  - **Known misreads.** Logs carry no `Sec-Fetch-Dest` and no body, so: a Next.js client-side navigation (an `?_rsc=` fetch) reads like the prefetch of every link in view, and both are left out, so an SPA click without a document load is not counted; an extensionless API reference page at the root (`/api/...`) and GraphiQL read as resources, and a sub-path API (`/shop/api/cart`) as a page; GraphQL query posts, view-counter posts and WordPress's own Heartbeat posts (action in the body) read as actions; a page's own CSV or text fetch counts as a page load; a non-Shopify page whose URL carries `section_id` or `sections` reads as a resource.
  - **Trust (owner's choice: "app files only").** For a browser agent, `isScannerPath(path, { browser: true })` spares what a web app's pages load or link to by themselves (`BROWSER_APP_ROOT_FILE` and `BROWSER_APP_ENDPOINT` in `agent-trust.ts`): Blazor and single-page-app settings files at the site root, Azure App Service's sign-in endpoints under `/.auth/`, and Netlify Identity and Git Gateway. Inside a spared endpoint the key, credential and secret-file checks still run as at the site root, and any other `/.auth/` path is a hidden-folder probe. Everything else stays a probe, `/wp-login.php` included (a brute-forcer spoofing an agent must not read as agent sign-ins). The settings files, `/.auth/me`, `/.auth/refresh` and the Netlify endpoints are resources; a sign-in, sign-out or purge is a page load the agent made, so it counts and shows in its journey. The cost: a scanner that spoofs a browser agent and asks only for these paths no longer marks its other requests (its `.env`, `.git` and other probes still do). The stored-traffic pass applies the same check.
  - **Journeys.** `extractAgentJourneyRequests` keeps a browser agent's page loads, its actions and any request that failed, with its status (`keepsBrowserAgentJourneyRequest`), and drops its other resources, so a journey never shows a page it only prefetched or credits an Advanced Property for an image-optimizer or beacon call. Reads say what they leave out in `coverage.limitations` (`BROWSER_AGENT_LIMITATION` in api-routes `agent-journeys.ts`); change it with this rule. The stored-traffic pass removes the stored requests capture now drops (`agentRequests.pageResources`); stored rows keep no query, so a stored `?_rsc=` prefetch stays until retention drops it.
  - **History (owner's choice: "keep and mark").** Stored hourly rows stay as recorded and were not recounted. Google-Agent's counted every request. Claude-Agent, stored as an unrecognized agent before its rule, counted its GET and HEAD requests for anything but a static file, and the stored-traffic pass moves those hours into the AI user fetch counts. The older trust rules also sent whole browser-agent visits to the likely fake counts. `traffic_sources.ai_user_fetch_older_count_until` marks where each source's older count ends; `packages/db/AGENTS.md` (migration 222) says what sets and moves it. The API reports it as `aiUserFetchCountingChangedAt` (traffic events series, traffic analytics); `trends.aiUserFetchHits` fits only buckets that begin at or after it, and the analytics `aiUserFetchHits.deltaPct` is null while the prior window starts before it, as the AI-referral arrival change is handled. Totals and points keep the stored counts.
  - A new hosted browser gets `browser: true` on its rule. Bump `BROWSER_AGENT_REQUEST_RULES_VERSION` when a change to `browserAgentRequestKind`, `countsAsAiUserFetchHit` or `keepsBrowserAgentJourneyRequest` alters what counts or which journey requests stay. Either change alters the stored-traffic pass's fingerprint, so `canonry serve` runs the pass again: it marks every source holding browser-agent hours and removes the stored journey requests capture now drops. The Cloudflare Worker still forwards every request of a keyword agent; dropping its static files at the edge would only save deliveries.
- **Reviewed, low-churn publisher snapshots.** Runtime classification never fetches the network. `.github/workflows/refresh-crawler-ip-ranges.yml` checks every official source weekly and opens one fixed-branch PR only when canonical prefix content or the canonical source URL changes. Publisher timestamp/order-only changes preserve the existing snapshot. A partial source failure exits nonzero and opens no PR. Amazon's official HTML pages and Anthropic's Claude-Agent SAIL file (TOML, `draft-kelley-webbotauth-sail-00`) are normalized into the same validated manifest shape by `scripts/refresh-ip-ranges.ts`. Its SAIL reader takes only the TOML subset that file uses and throws on any other syntax or a new draft revision. It applies the draft's validity rules (case-insensitive names, prefixes listed on a service count as an anonymous set, a required expiry, globally reachable unicast prefixes only, no dangling references), fails on a carve-out a flat prefix list cannot express, and does not act on the file's expiry, since the vendored copy refreshes weekly.
- **Rule order.** `classifyCrawler` and `classifyAiUserFetch` return the first rule that matches, so a specific rule must sit above any broader pattern that also matches it. The "classifier rule order" test in `analysis.test.ts` checks that each rule's literal user-agent tokens (read from its patterns by `test/fixtures/rule-tokens.ts`) classify to that rule, in its own channel only, and the Cloudflare Worker test checks that the Worker forwards each one. A non-literal pattern needs its tokens listed in the fixture, or the test fails. Do not add a pattern that matches bots no rule names, such as the removed `Claude-[A-Z]+Bot/`: a bot an operator adds later must arrive as an unrecognized agent, not count as one of its known bots. Broader patterns that already ship are known exceptions: the `Googlebot[/-]` family, `anthropic-ai`, the open-left `ClaudeBot/`, `Google-Agent` and `Diffbot`. An unrecognized agent keeps only its GET and HEAD hits for anything but a static file; the rest count only in `unknownHits`. Only `canonry serve` sends `traffic.agent.discovered` (`packages/canonry/src/unrecognized-agent-alerts.ts`). The name must reach 3 stored hits within 7 days of first detection. Names from the first 7 days of recorded project traffic are ineligible. Only webhooks subscribed before the first decision receive the alert.
- **Splitting a rule.** Stored history moves through a migration (v65 Mistral, v221 Claude-SearchBot), which moves an hourly row only whole, by its one sampled user agent. A migration runs once, so the stored-traffic pass (`rekeyCrawlerHours` in `packages/canonry/src/traffic-reclassify.ts`) also files each crawler hour whose sampled user agent today's rules file elsewhere where ingest would: under another crawler rule, in the AI user fetch counts, back in the unrecognized agents, or nowhere for Canonry's own tools. Such hours include ones an older version wrote after a rollback. An hour keeps its verification only on a move between two rules that check the same published list (`rulesShareVerificationList`). What the automatic pass holds back, and the rollbacks it cannot see: `packages/canonry/AGENTS.md`, "Stored-traffic reclassification".
- **Self-traffic exclusion.** `buildTrafficProbeReport` drops events whose UA matches `SELF_TRAFFIC_USER_AGENT_PATTERNS` (Canonry's own tooling, e.g. `AINYC-AEO-Audit/` from `agent-readiness --sitemap`) before any rollup. Our own measurement crawls a client's sitemap/robots/llms.txt/pages and is not a real visitor or third-party crawler, so it must never inflate a client's crawler / unknown / total counts or pollute the sample tail. The dropped count is surfaced as `totals.selfTrafficExcluded` (never silent). `isSelfTraffic(event)` is the shared predicate; keep its patterns specific so a real UA that merely mentions the brand is not swept up.
- **Path normalization.** Rollups key on the normalized path so query-string variants don't fragment the bucket counts.
- **Journeys stay generic.** Journey logic reads only `NormalizedTrafficRequest` fields, so every adapter feeds it the same way. No site-specific paths, goals or snippets. A request from a different outside source starts a new visit; a same-site referer is a step inside one.
- **Bounded sample tail.** `buildTrafficProbeReport` keeps a small sample slice for classifier debugging; the durable signal is the hourly bucket counts.
- **Agent requests are observed evidence, not tasks.** Agent journey capture uses `classifyAiUserFetch`, separate from human AI-referral journeys. Operator verification does not prove a session, action, task, or outcome. No-IP requests remain unlinked; never group a shared UA into one agent journey. JSON responses remain eligible even though the general crawler path classifier calls them assets.

## Common Mistakes

- **Adding I/O here.** Network/file/DB calls belong in adapters or service code. Keep this package pure.
- **Treating UA-only matches as verified.** Anyone can spoof a user agent. Promote above `claimed_unverified` only when `verifyIpForRuleDecision` confirms the source IP against the operator's published range. Keep `verifyIpForRule` only for callers that need the legacy boolean result.
- **Mixing crawler and referral signals into one bucket.** They answer different questions (machine activity vs human clicks); keep them in separate tables and separate API surfaces.
- **Counting every request that carries an AI engine's utm as an arrival.** The landing page's utm rides the referer of every later page, asset and API call of the visit, and a session window does not span a visit: a source that logs page HTML read about one arrival per minute of every visit. Only the arrival counts (`findAiReferralFollowOns`).
